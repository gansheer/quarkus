= Extending Your Quarkus Application with Apache Camel
include::_attributes.adoc[]
:categories: integration
:summary: This guide shows how to extend an existing Quarkus REST application with Apache Camel for Kafka events, HTTP service calls, and file ingestion.
:topics: camel,integration,kafka,file
:extensions: org.apache.camel.quarkus:camel-quarkus-direct,org.apache.camel.quarkus:camel-quarkus-kafka

You have a Quarkus application with REST endpoints, a service layer, maybe a database.
Then a new requirement comes in: send an event to Kafka when an order is placed.
Then another: notify a partner system via HTTP, with retries when their API is down.
And another: ingest CSV order files from a partner directory.

Each of these is an integration task.
https://camel.apache.org/[Apache Camel] is a lightweight integration library with https://camel.apache.org/components/[400+ connectors] designed for exactly this.
With https://camel.apache.org/camel-quarkus/[Camel Quarkus], it runs inside your application as any other CDI bean: same `application.properties`, same `quarkus dev`, same native compilation support.

This guide starts from an order management REST API and progressively adds these three integrations using Camel.

image::camel-qs-architecture.png[alt=Architecture overview showing the existing Quarkus REST application extended with three Camel routes for Kafka events and HTTP and file ingestion,align=center]

== The starting point

Consider a simple order management REST API:

[source,java]
----
@Path("/api/orders")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class OrderResource {

    @Inject
    OrderRepository repository;

    @GET
    public List<Order> list() {
        return repository.listAll();
    }

    @POST
    public Response create(Order order) {
        repository.add(order);
        return Response.status(Response.Status.CREATED).entity(order).build();
    }
}
----

`Order` is a POJO with four fields (`id`, `customer`, `type`, `amount`).
`OrderRepository` is an `@ApplicationScoped` CDI bean that stores orders in memory.

Camel routes are CDI beans that extend `RouteBuilder`.
Quarkus discovers them like any other bean:

[source,java]
----
@ApplicationScoped
public class MyRoutes extends RouteBuilder {
    @Override
    public void configure() {
        // routes go here
    }
}
----

At this point, nothing has changed in your existing code.
Your REST endpoints, services, and beans are unaffected.

== Sending order events to Kafka

The first requirement: every time an order is placed, publish an event to a Kafka topic so downstream systems can react to it.

The change to the existing code is two lines:

[source,java]
----
@Path("/api/orders")
@Produces(MediaType.APPLICATION_JSON)
@Consumes(MediaType.APPLICATION_JSON)
public class OrderResource {

    @Inject
    OrderRepository repository;

    @Inject
    ProducerTemplate producerTemplate; // <1>

    @GET
    public List<Order> list() {
        return repository.listAll();
    }

    @POST
    public Response create(Order order) {
        repository.add(order);
        producerTemplate.sendBody("direct:order-placed", order); // <2>
        return Response.status(Response.Status.CREATED).entity(order).build();
    }
}
----
<1> Inject `ProducerTemplate`, Camel's bridge from existing code into a route. In Camel Quarkus, it is automatically available as a CDI bean.
<2> Push the order object into the `direct:order-placed` endpoint, which is the entry point of the Camel route.

A _route_ in Camel is a processing pipeline: it starts from an input (a URI like `direct:`, `kafka:`, or `file:`), applies a chain of steps (transformation, filtering, logging), and sends the result to one or more outputs.

Here is the Camel route:

[source,java]
----
@ApplicationScoped
public class OrderEventRoute extends RouteBuilder {

    @Override
    public void configure() {
        from("direct:order-placed")
            .routeId("order-event")
            .marshal().json()
            .to("kafka:order-events")
            .log("Order event sent to Kafka");
    }
}
----

And the Kafka configuration in `application.properties`:

[source,properties]
----
camel.component.kafka.brokers=${kafka.bootstrap.servers:localhost:9092}
----

The route does three things: receive the order, serialize it to JSON, send it to Kafka.

Create an order and watch the console:

[source,bash]
----
curl -s -X POST http://localhost:8080/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"id":"ORD-002","customer":"Global Inc","type":"standard","amount":250.00}'
----

In the logs:

[source,text]
----
... order-event ... Order event sent to Kafka
----

The order is persisted and published to Kafka.

*Extensions used:* `camel-quarkus-kafka`, `camel-quarkus-jackson`, `camel-quarkus-direct`

== Notifying the loyalty system

The next requirement: also call the partner's loyalty API over HTTP so customers earn points when they place an order.
The partner's API is unreliable, so the call needs retries with backoff.

The order event route already handles the Kafka step.
Add the loyalty notification to the same route, plus an error policy:

[source,java]
----
@ApplicationScoped
public class OrderEventRoute extends RouteBuilder {

    @Override
    public void configure() {
        onException(Exception.class)
            .maximumRedeliveries(3)
            .redeliveryDelay(1000)
            .backOffMultiplier(2)
            .retryAttemptedLogLevel(LoggingLevel.WARN)
            .handled(true)
            .log(LoggingLevel.ERROR,
                    "Order event processing failed: ${exception.message}");

        from("direct:order-placed")
            .routeId("order-event")
            .marshal().json()
            .to("kafka:order-events")
            .log("Order event sent to Kafka")
            .setHeader("Content-Type", constant("application/json"))
            .to("http://{{loyalty.api.url}}/api/loyalty/notify")
            .log("Loyalty service notified");
    }
}
----

The `onException` block retries any failed step up to 3 times with exponential backoff, each attempt logged at WARN level.
If the loyalty API returns a 500 or the connection times out, Camel retries automatically.
If all attempts fail, it logs the error and moves on -- the order is still safely persisted, since that happened before the Camel call.

Add the loyalty API URL to `application.properties`:

[source,properties]
----
loyalty.api.url=loyalty.example.com
----

Create another order and watch both integrations fire:

[source,bash]
----
curl -s -X POST http://localhost:8080/api/orders \
  -H 'Content-Type: application/json' \
  -d '{"id":"ORD-003","customer":"Stark Industries","type":"priority","amount":8900.00}'
----

In the logs:

[source,text]
----
... order-event ... Order event sent to Kafka
... order-event ... Loyalty service notified
----

Both integrations are triggered from the same `sendBody` call.

*Extension used:* `camel-quarkus-http`

== Ingesting files from a partner

The third requirement: a partner drops CSV order files into a directory.
The application should parse each file, ingest the orders, and move the original to a `done` directory.
Failed files go to a `failed` directory.

Camel handles this with a self-contained route:

[source,java]
----
@ApplicationScoped
public class FileProcessingRoute extends RouteBuilder {

    @Override
    public void configure() {
        CsvDataFormat csv = new CsvDataFormat();
        csv.setSkipHeaderRecord(true);

        from("file:{{file.orders.incoming:orders/incoming}}?include=.*\\.csv"
                + "&move=../done&moveFailed=../failed"
                + "&readLock=changed")
            .routeId("file-ingestion")
            .log("Processing file: ${header.CamelFileName}")
            .unmarshal(csv)
            .split(body())
                .bean("orderConverter")
                .bean("orderRepository", "add")
            .end()
            .log("File processed: ${header.CamelFileName}");
    }
}
----

The `file` component handles polling, read-locking (no partial reads), and move-on-success/failure through URI options.
Camel's built-in `CsvDataFormat` parses the file content into rows, skipping the header.
After `split(body())`, each exchange carries one row as a `List<String>`.

`orderConverter` is a bean that maps each row to an `Order`:

[source,java]
----
@ApplicationScoped
@Named("orderConverter")
@RegisterForReflection
public class OrderConverter {

    public Order fromCsvRow(List<String> row) {
        return new Order(
                row.get(0).trim(),
                row.get(1).trim(),
                row.get(2).trim(),
                new BigDecimal(row.get(3).trim()));
    }
}
----

`orderRepository` is your existing CDI bean, referenced by name.
For Camel to look it up by name, add `@Named("orderRepository")` and `@RegisterForReflection` to `OrderRepository`.

Drop a CSV file and verify:

[source,bash]
----
cat > orders/incoming/orders.csv << 'EOF'
id,customer,type,amount
ORD-010,Acme Corp,priority,1500.00
ORD-011,Wayne Enterprises,standard,250.00
ORD-012,Stark Industries,priority,8900.00
EOF
----

In the logs:

[source,text]
----
... file-ingestion ... Processing file: orders.csv
... file-ingestion ... File processed: orders.csv
----

[source,bash]
----
curl -s http://localhost:8080/api/orders
----

You will see the orders from the CSV file alongside any you created via the REST API.
The original file has been moved to `orders/done/`.
A malformed file would go to `orders/failed/` instead.

*Extensions used:* `camel-quarkus-file`, `camel-quarkus-csv`, `camel-quarkus-bean`

== What changed in your existing code

Three integration capabilities were added: Kafka events, HTTP API calls with retries, and file ingestion.
The existing code changed by three lines:

1. `@Inject ProducerTemplate producerTemplate` -- one new field in `OrderResource`.
2. `producerTemplate.sendBody("direct:order-placed", order)` -- one new call in `OrderResource`.
3. `@Named("orderRepository")` and `@RegisterForReflection` on `OrderRepository` -- so Camel can look it up by name, including in native builds.

Everything else is new classes (`RouteBuilder` implementations, `OrderConverter`) that live alongside the existing code.
The file ingestion route does not touch the REST layer at all.

== Camel and Quarkus coexistence

Camel Quarkus integrates with the Quarkus runtime:

*CDI beans are shared.*
Any bean with `@Named` or `@Identifier` is available in Camel routes via `.bean("beanName")`.
You can also look up beans by type with `.bean(MyService.class)`.

*REST endpoints coexist.*
Jakarta REST endpoints continue to be served by Quarkus HTTP.
Camel routes that use `platform-http` share the same HTTP server.

*Same configuration.*
Camel settings go in the same `application.properties`, under the `camel.*` namespace.
Quarkus profiles, config sources, and environment variable overrides all apply.

*Dev mode.*
`quarkus dev` hot-reloads Camel routes along with everything else.

*Native compilation.*
Camel Quarkus extensions are built for GraalVM native image.
Adding Camel routes does not break native compilation.

== Going further

This guide covered three patterns, but Camel's 400+ components cover databases, cloud services, messaging systems, SaaS APIs, and protocols from FTP to AS2.
Each follows the same model: add the `camel-quarkus-*` extension, use its URI in a route.

Camel implements the https://camel.apache.org/components/eips/enterprise-integration-patterns.html[Enterprise Integration Patterns].
Here are a few that would naturally extend this example:

* *Content-Based Router:* use `.choice().when()` to route priority orders to a fast-track queue and standard orders to the normal flow.
* *Wire Tap:* use `.wireTap("seda:audit")` to send a copy of the order event to an audit log without slowing down the main route.
* *Throttle:* use `.throttle(10)` to rate-limit calls to the partner loyalty API.
* *Dead Letter Channel:* replace the `onException` log-and-swallow with `errorHandler(deadLetterChannel("file:orders/errors"))` to persist failed order events to disk for later inspection or reprocessing.
